# قالب دستور پخت Cookwala: دستورهایی که با Missionها کار می‌کنند

یک دستور پخت در Cookwala فهرستی از دستورالعمل‌ها نیست. بلکه **دانش پخت‌وپز قابل حمل** است
که یک برنامه‌ریز آن را در برابر یک Mission مشخص (household، ربات‌ها، لوازم خانگی،
انرژی، بودجه، سلامت، زمان‌بندی) به یک برنامه قابل اجرا *تدوین* می‌کند. سپس ربات آن برنامه را اجرا کرده
و با تغییر واقعیت، از طریق contingencies و playbooks خود را تطبیق می‌دهد.

طرحواره: [`recipe.schema.json`](../schemas/recipe.schema.json). مثال کامل اجرا شده:
[`examples/shakshuka.cookwala.json`](../examples/shakshuka.cookwala.json).

## ۱. چهار لایه (اقتباس شده از رویکرد WHO SMART Guidelines)

| لایه | آنچه در بر دارد | چه کسی آن را می‌نویسد | کجا قرار دارد |
|---|---|---|---|
| **R1 Narrative** | متن دستور پخت انسانی، داستان، یادداشت‌های فرهنگی، عکس‌ها | آشپزها، سرآشپزها، fifi.cooking | `text`, `dish.images` |
| **R2 Dish spec** | آنچه غذا *هست* و *باید باشد*: هویت (ضروری در مقابل منعطف)، اهداف حسی، تغذیه، سبک سرو و خوردن، نگهداری، بررسی‌های پذیرش | ویرایشگران دستور پخت، با کمک AI، بازبینی شده | `identity`, `sensory`, `service`, `storage`, `nutrition`, `acceptance` |
| **R3 Executable IR** | روش مستقل از دستگاه: فرمول (نسبت‌ها + نقش‌ها)، گراف فرآیند از ops تایپ‌شده با شرایط پیش/پس از وضعیت غذا، شرایط `until`، جایگزین‌ها، قوانین توقف، حالت‌های شکست، امکان‌دهی‌ها، مخاطرات، CCPs، آماده‌سازی محیط | خط لوله خروجی + بازبینی؛ تأیید شده توسط simulator (V2) | `formula`, `ingredients`, `equipment`, `prep`, `process`, `safety` |
| **R4 Bound plan** | دستور پخت R3 کامپایل شده برای *این* Mission: مقادیر دقیق، انواع انتخاب شده، بازیگران و دستگاه‌های اختصاص یافته، برنامه زمانی، اجاره‌ها، مانیتورها، شرایط پیش‌بینی نشده | برنامه‌ریز/کامپایلر، در زمان اجرا | داخل **Mission** (`plan`)، هرگز در کاتالوگ |

مانند کد منبع و یک کامپایلر: **دستور پخت یک بازنمایی میانی قابل حمل است (R3 + R2). ماموریت، ماشین هدف است.** این همان چیزی است که دستور پخت‌ها را با تغییر ربات‌ها و هوش مصنوعی معتبر نگه می‌دارد: یک برنامه‌ریز بهتر، یک R4 بهتر از همان دستور پخت تولید می‌کند.

## ۲. هر بخش در یک Mission چه کاری انجام می‌دهد

| بخش دستور پخت | مورد استفاده توسط Mission برای... |
|---|---|
| `identity.essential / flexible / neverAdd` | جایگزینی‌ها، حالت‌های بودجه و جیره، انطباق‌های رژیم غذایی: تغییر بخش‌های flexible، هرگز بخش‌های essential را، تا غذا همچنان خودش باقی بماند |
| `formula` (ratios, min/max, role, scaling) | مقیاس‌بندی دقیق برای هر تعداد نفر، جیره‌بندی مواد اولیه در طول یک هفته، کشیدن بودجه، استفاده از آنچه در دسترس است (rescale با محدودیتِ ماده اولیه) |
| `sensory` | نقاط بازرسی بینایی، رایحه و طعم؛ پروفایل‌های طعم household (نمک ۲ در مقابل ۴)؛ تصمیمات مربوط به تغییر کاربری و اصلاح |
| `prep` (tools, surfaces, clearFirst, advanceTasks) | **وظایف آماده‌سازی محیط:** اگر سینک یا اجاق اشغال شده باشد، برنامه‌ریز وظایف "clear, wash, dry" را اضافه می‌کند؛ وظایف soak یا thaw ساعت‌ها قبل برنامه‌ریزی می‌شوند |
| `process.nodes[]` با حالت‌های غذایی `pre`/`post` | برنامه‌ریزی (فقط شروع آنچه آماده است)، تأیید (آیا آن مرحله حالت مورد نظر را تولید کرد؟)، ادامه پس از وقفه‌ها |
| `until`, `onTimeout`, `retry` | دانستن اینکه چه زمانی یک مرحله تمام شده است و چه کاری باید انجام داد وقتی تمام نشده است |
| `alternatives[]` + `energy` | گاز در مقابل القایی در مقابل فر، صرفه‌جو در باتری، آشپزخانه‌های بدون فر، ساعات آرام |
| `pause` (pausable, safeState, maxPause, onExceeded) | **وقفه‌ها:** یک کودک نیاز به کمک دارد، مالک تماس می‌گیرد، سگ چیزی را واژگون می‌کند. ربات مرحله را در safeState قرار می‌دهد، رویداد را مدیریت می‌کند، سپس بر اساس بودجه pause، از حالت ادامه، گرم کردن مجدد، نجات یا دور ریختن استفاده می‌کند |
| `failureModes` (incident, detect, prevent, playbook) | تشخیص زودهنگام مشکلات شناخته شده و playbook دقیق برای بازیابی |
| `affordances`, `space` | تطبیق مراحل با ربات‌هایی که می‌توانند گیرنده‌، بلندکننده و دسترسی داشته باشند؛ دور نگه داشتن مناطق داغ از کودکان |
| `safety` (hazards, CCPs, supervision, abort) | هسته safety: invariantهایی که هر برنامه باید حفظ کند |
| `service` (temps, vessel, accompaniments, tableware, eating style, portioning, packable) | سرو کردن: آنچه روی میز، در اتاق، یا در ظرف ناهار قرار می‌گیرد؛ یادآوری‌ها و محدودیت‌های نگهداشت؛ سبک خوردن فرهنگی |
| `storage` | باقی‌مانده‌ها، Missionهای پخت از قبل و ظرف ناهار |
| `acceptance` | *تست‌های* دستور پخت: Mission زمانی تمام می‌شود که این‌ها برقرار باشند |
| `nutrition`, `cost` | بخش‌های شخصی، بودجه، جیره‌های امدادی |

## ۳. مثال: یک مرحله با تمام موارد پیوست شده

```json
{
  "id": "n7", "op": "cw.op.simmer",
  "inputs": ["aromatic_base", "tomato", "salt", "blackpepper"], "output": "sauce",
  "params": { "heat": "medium_low", "lid": "off", "target": { "sensor": "cw.sense.liquid_temp", "value": 94, "unit": "degC", "tolerance": 3 } },
  "until": { "any": [ { "sensor": "cw.sense.mass_loss_ratio", "gte": 0.25 }, { "vision": "cw.sense.sauce_coats_spoon" } ],
             "minTime": "PT10M", "maxTime": "PT18M" },
  "onTimeout": "extend",
  "pause": { "pausable": true, "safeState": ["heat_hold_low", "lid_ajar"], "maxPause": "PT45M", "onExceeded": "reheat_then_resume" },
  "failureModes": [
    { "incident": "cw.incident.too_salty", "likelihood": "low", "playbook": "cw.pb.too_salty_liquid" },
    { "incident": "cw.incident.too_thin", "likelihood": "medium", "playbook": "cw.pb.sauce_too_thin" } ],
  "alternatives": [ { "id": "gas", "op": "cw.op.simmer", "when": ["gas_only"], "timeFactor": 1.0, "quality": "same" } ],
  "hazards": ["hz_splatter", "hz_steam"], "attention": "monitor"
}
```

## ۴. تدوین یک دستور پخت برای یک Mission (آنچه برنامه‌ریز انجام می‌دهد)

1. **انتخاب گونه:** انتخاب رژیم غذایی، بافت (IDDSI)، تجهیزات، انرژی و حالت از میان
   `alternatives`. ضروریات هویت باید حفظ شوند.
2. **مقیاس‌بندی:** بر اساس `formula` و وعده‌ها، سهم هر نفر (HEALTH.md)،
   ماده محدودکننده، یا افق جیره. ادویه‌ها به صورت زیرخطی، زمان بر اساس توان جرم.
3. **جایگزینی** در چارچوب نقش‌ها، با رعایت `identity.neverAdd` ، آلرژن‌ها، بسته‌های رژیمی
   و موجودی.
4. **آماده‌سازی محیط:** مقایسه `prep` با فست‌های فضایی ماموریت (سینک پر است؟
   اجاق اشغال شده است؟ تخته کثیف است؟) و افزودن وظایف مرتب‌سازی، شستشو، خشک کردن و مرحله‌بندی. زمان‌بندی
   `advanceTasks` (خیساندن، یخ‌زدایی، مرینیت کردن، پیش‌گرم کردن).
5. **اتصال:** اختصاص هر گره به ربات‌ها، لوازم خانگی یا انسان‌ها بر اساس امکانات و
   قابلیت‌ها. اجاره شعله‌ها، ظروف و مناطق. اتصال مانیتورها (قاب هوشمند، زمان تخمینی رسیدن (ETA)،
   آشکارساز دود).
6. **زمان‌بندی** معکوس از زمان سرو، با احترام به بودجه‌های توقف، محدودیت‌های باتری و انرژی،
   ساعات آرامش خانوار و بازه‌های اشتراک‌گذاری آشپزخانه.
7. **پیوست کردن شرایط اضطراری:** قوانین `failureModes` و `pause` هر گره، به‌علاوه
   سیاست‌های جهانی ماموریت (اختلالات، حضور کودک یا حیوان خانگی نزدیک اجاق، نگهبان اجاق،
   ناظر فساد مواد).
8. **تایید:** بررسی‌های طرحواره + معنایی، بسته‌های سیاست، پوشش CCP، dry run شبیه‌ساز،
   ناورایی‌های پشته اولویت (PROTOCOL §7.2).
9. **انتشار R4** در `plan` ماموریت، امضای آن، و تحویل آن به ربات.

## 5. نویسندگی و تبدیل

- **از fifi.cooking:** خط لوله EXPORT-FIFI مقادیر R1 + R2 + R3 را تولید می‌کند. بخش‌های جدید (identity, sensory, formula, prep, service, pause, failureModes, affordances) توسط مدل‌های محلی از متن موجود تولید شده و توسط اعتبارسنج‌ها و بازبینی نمونه‌برداری شده توسط انسان بررسی می‌شوند.
- **از وب:** `cookwala convert --from schema-org` ← R1/R2 (V0)، سپس همان غنی‌سازی.
- **به سایر فرمت‌ها:** schema.org Recipe (R1/R2 برای موتورهای جستجو)، Cooklang (ویرایش انسانی)، PDDL یا منطق زمانی (برنامه‌ریزان پژوهشی) همگی می‌توانند از R3 تولید شوند.
- **به صورت دستی:** `cookwala init recipe` تمام لایه‌ها را ایجاد می‌کند؛ `cookwala validate` و `cookwala simulate` آن‌ها را بررسی می‌کنند.
- **نسخه‌بندی:** بازبینی‌ها تغییرناپذیر و هش‌شده هستند. شاخه‌ها (Forks) `meta.derivedFrom` را ثبت می‌کنند. **patches** دستورالعمل‌ها (از playbookها یا بازخوردها) به عنوان diff پیشنهاد می‌شوند و تنها پس از بازبینی و شواهد ارتقا می‌یابند.

## ۶. زبان متن مرحله

جملات گام‌به‌گام ابتدا برای یک شخص نوشته می‌شوند و در مرحله دوم توسط یک ماشین تجزیه می‌گردند. متن گام عربی در دستور پخت‌های نمونه از امر مؤنث (قطّعي، سخّني) استفاده می‌کند که قرارداد رایج کتاب‌های آشپزی مصری است؛ این یک انتخاب آگاهانه است و نه یک سهو، و یک ناشر ممکن است به جای آن از مجهول بدون جنسیت (تُقطَّع البصلة) استفاده کند. فیلدهای `op` ،`params` و `until` معنا را منتقل می‌کنند؛ جمله برای آشپز است.

## ۷. چرا این آینده‌نگرانه باقی می‌ماند

- دستورالعمل‌ها **پیامدها و محدودیت‌های غذا، و نه حرکات** را توصیف می‌کنند. ربات‌های جدید و هوش مصنوعی جدید، برنامه‌های R4 بهتری از همان R3 تولید می‌کنند.
- تمام بخش‌های جدید **اختیاری و افزایشی** هستند. یک دستورالعمل V0 (فقط R1) همچنان برای پخت‌وپز هدایت‌شده توسط انسان کار می‌کند؛ هر لایه اضافه‌شده، اتوماسیون بیشتری را باز می‌کند.
- فیلدهای ناشناخته `x-` عبور داده می‌شوند. فروشندگان، سرآشپزها و نهادهای بهداشتی می‌توانند دستورالعمل‌ها را بدون ایجاد اختلال برای دیگران گسترش دهند.
- **بررسی‌های پذیرش** به هر اجراکننده، چه انسان و چه ربات، اجازه می‌دهند ثابت کنند که غذا درست تهیه شده است، که این همان روشی است که دستورالعمل‌ها با شواهد میدانی به V3 می‌رسند.
