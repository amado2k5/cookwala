# Формат рецептов Cookwala: рецепты, которые работают с Missions

Рецепт в Cookwala — это не список инструкций. Это **переносимые кулинарные знания**, которые планировщик *компилирует* с учетом конкретной Mission (household, robots, appliances, energy, budget, health, timing) в исполняемый план. Затем робот выполняет этот план, адаптируясь к непредвиденным обстоятельствам и используя playbooks, когда реальность меняется.

Схема: [`recipe.schema.json`](../schemas/recipe.schema.json). Полный рабочий пример:
[`examples/shakshuka.cookwala.json`](../examples/shakshuka.cookwala.json).

## 1. Четыре слоя (адаптировано на основе подхода WHO SMART Guidelines)

| Слой | Что содержит | Кто записывает | Где находится |
|---|---|---|---|
| **R1 Narrative** | Текст рецепта от человека, история, культурные заметки, фото | Повара, шеф-повара, fifi.cooking | `text`, `dish.images` |
| **R2 Dish spec** | Что блюдо *есть* и чем оно *должно быть*: идентичность (существенная vs гибкая), сенсорные цели, питание, стиль подачи и приема пищи, хранение, проверки принятия | Редакторы рецептов, с помощью AI, проверено | `identity`, `sensory`, `service`, `storage`, `nutrition`, `acceptance` |
| **R3 Executable IR** | Агностический к устройствам метод: формула (соотношения + роли), граф процесса типизированных ops с pre/post условиями состояния еды, условия `until`, альтернативы, правила паузы, режимы отказа, аффордансы, опасности, CCPs, подготовка среды | Конвейер экспорта + проверка; проверено симулятором (V2) | `formula`, `ingredients`, `equipment`, `prep`, `process`, `safety` |
| **R4 Bound plan** | Рецепт R3, скомпилированный для *этой* Mission: точные количества, выбранные варианты, назначенные акторы и устройства, расписание, лизинги, мониторы, непредвиденные обстоятельства | Планировщик/компилятор, во время выполнения | Внутри **Mission** (`plan`), никогда в каталоге |

Как исходный код и компилятор: **рецепт — это переносимое промежуточное представление (R3 + R2). Mission — это целевая машина.** Именно это позволяет рецептам оставаться валидными при изменении роботов и ИИ: лучший планировщик создает лучший R4 из того же рецепта.

## 2. Что делает каждый раздел в Mission

| Секция рецепта | Используется Миссией для… |
|---|---|
| `identity.essential / flexible / neverAdd` | Замены, режимы бюджета и рационов, адаптация диеты: изменение гибких частей, но никогда — основных, чтобы блюдо оставалось собой |
| `formula` (ratios, min/max, role, scaling) | Точное масштабирование на любое количество человек, распределение ингредиентов по рациону на неделю, растягивание бюджета, использование того, что есть под рукой (пересчет по ограничивающему ингредиенту) |
| `sensory` | Контрольные точки зрения, аромата и вкуса; профили вкуса household (соль 2 против 4); решения по перепрофилированию и исправлению |
| `prep` (tools, surfaces, clearFirst, advanceTasks) | **Задачи по подготовке окружения:** если раковина или варочная панель заняты, планировщик добавляет задачи «очистить, вымыть, высушить»; задачи по замачиванию или размораживанию планируются за несколько часов |
| `process.nodes[]` с состояниями еды `pre`/`post` | Планирование (начинать только то, что готово), верификация (привело ли действие к нужному состоянию?), возобновление после прерываний |
| `until`, `onTimeout`, `retry` | Понимание того, когда шаг завершен и что делать, если он не завершен |
| `alternatives[]` + `energy` | Газ против индукции против духовки, режим экономии заряда батареи, кухни без духовки, часы тишины |
| `pause` (pausable, safeState, maxPause, onExceeded) | **Прерывания:** ребенку нужна помощь, владелец зовет, собака что-то опрокинула. Робот переводит шаг в его safeState, обрабатывает событие, затем возобновляет, разогревает, спасает или утилизирует, исходя из бюджета паузы |
| `failureModes` (incident, detect, prevent, playbook) | Раннее обнаружение известных проблем и точный playbook для восстановления |
| `affordances`, `space` | Сопоставление шагов с роботами, которые могут захватывать, поднимать и дотягиваться; удержание горячих зон вдали от детей |
| `safety` (hazards, CCPs, supervision, abort) | Ядро безопасности: инварианты, которые должен сохранять каждый план |
| `service` (temps, vessel, accompaniments, tableware, eating style, portioning, packable) | Подача: что идет на стол, в комнату, в ланчбокс; напоминания и лимиты ожидания; культурный стиль приема пищи |
| `storage` | Остатки еды, Mission по приготовлению заранее и ланчбоксам |
| `acceptance` | *Тесты* рецепта: Mission завершена, когда эти условия соблюдены |
| `nutrition`, `cost` | Персональные порции, бюджет, гуманитарные рационы |

## 3. Пример: один шаг со всеми прикрепленными данными

```json
{
  "id": "n7", "op": "cw.op.simmer",
  "inputs": ["aromatic_base", "tomato", "salt", "blackpepper"], "output": "sauce",
  "params": { "heat": "medium_low", "lid": "off", "target": { "sensor": "cw.sense.liquid_temp", "value": 94, "unit": "degC", "tolerance": 3 } },
  "until": { "any": [ { "sensor": "cw.sense.mass_loss_ratio", "gte": 0.25 }, { "vision": "cw.sense.sauce_coats_spoon" } ],
             "minTime": "PT10M", "maxTime": "PT18M" },
  "onTimeout": "extend",
  "pause": { "pausable": true, "safeState": ["heat_hold_low", "lid_ajar"], "maxPause": "PT45M", "onExceeded": "reheat_then_resume" },
  "failureModes": [
    { "incident": "cw.incident.too_salty", "likelihood": "low", "playbook": "cw.pb.too_salty_liquid" },
    { "incident": "cw.incident.too_thin", "likelihood": "medium", "playbook": "cw.pb.sauce_too_thin" } ],
  "alternatives": [ { "id": "gas", "op": "cw.op.simmer", "when": ["gas_only"], "timeFactor": 1.0, "quality": "same" } ],
  "hazards": ["hz_splatter", "hz_steam"], "attention": "monitor"
}
```

## 4. Составление рецепта для Mission (что делает планировщик)

1. **Выберите вариант:** диета, текстура (IDDSI), оборудование, выбор энергии и режима из
   `alternatives`. Основы идентичности должны быть сохранены.
2. **Масштабирование:** на основе `formula` и количества порций, порций на человека (HEALTH.md),
   ограничивающего ингредиента или горизонта рациона. Специи — сублинейно, время — по показателю массы.
3. **Замещение** в рамках ролей, соблюдая `identity.neverAdd`, аллергены, диетические наборы
   и инвентарь.
4. **Подготовка среды:** сравните `prep` с аспектами пространства Миссии (раковина полная?
   плита занята? доска грязная?) и добавьте задачи по уборке, мытью, сушке и подготовке. Запланируйте
   `advanceTasks` (замачивание, размораживание, маринование, предварительный нагрев).
5. **Связывание:** назначьте каждый узел роботам, приборам или людям на основе возможностей и
   компетенций. Арендуйте конфорки, сосуды и зоны. Прикрепите мониторы (умный горшок, расчетное
   ETA доставки, детектор дыма).
6. **Планирование** в обратном порядке от времени подачи, соблюдая бюджеты пауз, лимиты заряда
   батареи и энергии, часы тишины в household context и окна совместного использования кухни.
7. **Прикрепление непредвиденных обстоятельств:** `failureModes` и правила `pause` для каждого узла, плюс
   глобальные политики Миссии (прерывания, ребенок или питомец рядом с плитой, watchdog плиты,
   контроль порчи).
8. **Верификация:** проверка схемы + семантики, наборы политик, охват CCP, dry run симулятора,
   инварианты стека приоритетов (PROTOCOL §7.2).
9. **Выдача R4** в `plan` Миссии, подписание и передача роботу.

## 5. Создание и преобразование

- **From fifi.cooking:** конвейер EXPORT-FIFI генерирует R1 + R2 + R3. Новые
  разделы (identity, sensory, formula, prep, service, pause, failureModes, affordances)
  генерируются локальными моделями из существующего текста и проверяются валидаторами и
  выборочным человеческим анализом.
- **From the web:** `cookwala convert --from schema-org` → R1/R2 (V0), затем то же
  обогащение.
- **To other formats:** schema.org Recipe (R1/R2 для поисковых систем), Cooklang (ручное
  редактирование), PDDL или темпоральная логика (исследовательские планировщики) — всё это может быть сгенерировано из R3.
- **By hand:** `cookwala init recipe` создает каркас всех слоев; `cookwala validate` и
  `cookwala simulate` проверяют их.
- **Versioning:** ревизии неизменяемы и хешированы. Форки записывают `meta.derivedFrom`.
  **patches** рецептов (из playbooks или обратной связи) предлагаются в виде diffs и продвигаются только
  после проверки и наличия доказательств.

## 6. Язык текста шага

Предложения шагов написаны сначала для человека, а затем анализируются машиной. Текст шагов на арабском языке в примерах рецептов использует повелительное наклонение женского рода (قطّعي, سخّني), что является общепринятой египетской кулинарной традицией; это осознанный выбор, а не упущение, и издатель может использовать гендерно-нейтральный пассив (تُقطَّع البصلة) вместо этого. Поля `op`, `params` и `until` несут смысл; предложение предназначено для повара.

## 7. Почему это остается устойчивым к изменениям в будущем

- Рецепты описывают **результаты и ограничения по еде, а не движения**. Новые роботы и новый ИИ
  создают лучшие планы R4 из того же R3.
- Все новые разделы являются **необязательными и аддитивными**. Рецепт V0 (только R1) по-прежнему работает для
  управляемого приготовления пищи человеком; каждый добавленный слой открывает больше автоматизации.
- Неизвестные поля `x-` проходят сквозь систему. Поставщики, шеф-повара и органы здравоохранения могут расширять рецепты,
  не нарушая работу других.
- **Проверки соответствия** позволяют любому исполнителю, человеку или роботу, доказать, что блюдо получилось правильным,
  именно так рецепты переходят к V3 с полевыми доказательствами.
