Sample code for every role, in four languages

Clients, agents, orchestrators, gates, recovery and reporting for the Core 0.2 API, in Python, JavaScript, Java and C#. They run offline on simulated devices, or against any Cookwala hub. Every port tests itself against the reference implementation.

Samples, not certified software. The executor is always the authority: the gates check early so a client can explain a refusal, and the device checks everything again. Published on PyPI, npm and NuGet, with the single file and the .deb on GitHub Releases; each tile below says whether its channel is live yet (status per channel).

Try it: one minute, no install

  1. Run six orders on a simulated four-device kitchen. Standard library Python, nothing to install.

    git clone https://github.com/amado2k5/cookwala && cd cookwala/samples/python
python -m cookwala_samples demo
    6 runs: 3 completed, 1 failed, 1 refused, 1 stopped. Served 3, discarded 2, incidents reported 2, people asked 3 times.

  2. Or install it from a registry. The same command in every language; help explains each command, with examples.

    pip install cookwala-samples        # or: npm i -g @cookwala/samples · dotnet tool install -g Cookwala.Samples.Tool
cookwala-samples demo
cookwala-samples help run

  3. Ask the gates about one recipe on one device.

    python -m cookwala_samples gates koshari --device demo-hob-robot-basic --human-present
    "refusal": {"reason": "missing_sensor_no_fallback", "detail": "no way to verify cw.op.deep_fry on this device", "gate": "capability", "node": "n14"}

  4. Break something on purpose and watch the recovery.

    python -m cookwala_samples run koshari --human-present --fault 'example-koshari#n14=overheat' --format csv
    1-koshari,example-koshari,demo-hob-robot,stopped,,discard_and_report,discard,0,cw.incident.overheat

  5. Point it at a real hub. The same code, over HTTP.

    cookwala hub --port 7878 &
python -m cookwala_samples demo --hub http://localhost:7878

The six roles

Clients

One interface over HTTP and over a simulated executor. Retries reuse the Idempotency-Key, so a request is never cooked twice; stop is retried until it lands.

Agents

A planner acting under a signed mandate: scope, expiry and a confirm-before list. It never works around an allergen block and asks a person before anything irreversible. A monitor checks every state transition and temperature.

Orchestrators

Gates first, then a dry run on every device. The device that needs the fewest people wins. Start, poll, recover, collect the log, report. Optional by design: Cookwala works without one.

Gates

Core version, recipe hash, recall, mandate, allergen, untrusted text, envelope and local limits, attendance, device capability. The first refusal stops the request; a gate that fails refuses.

Recovery

Never retry around safety. A busy or unable device sends the request to the next one. A person is asked when needed; if nobody answers, it stops. After heat, a failed run means discard and report.

Reporting

A record per run and a summary, as JSON, Markdown, JUnit XML for CI dashboards, or CSV. Incident reports are anonymous: a date, no names, a random id.

Get the packages

One payload for the operating systems: the Python port has no dependencies, so a single file runs on any Python 3.9 or newer, and each package manager ships that file. The language registries ship their native port. Every tile links to the manifest in the repository.

The same code as a service

cookwala-samples serve, the container image and each cloud function call one handler:

EndpointAnswer
GET /healthliveness and version
POST /v1/samples/gatesthe gate decision for a recipe, a device, blocks and a mandate
POST /v1/samples/planthe planner's request and the device ranking
POST /v1/samples/runorchestrated jobs with injected faults, as a report
GET /v1/samples/demo?format=the demo report: json, markdown, junit, csv

The service talks only to its own simulated devices, never to another host, so a public function cannot be used to reach anyone's kitchen.

Kept honest by tests

  • Every port checks canonical JSON, recipe hashes and 32 dry runs against answers computed by the reference library (samples/data/bundle.json).
  • The Python tests compare the dry run with tools/cookwala_ref.py for every example recipe and device, and validate every request, status, log and incident against the JSON Schemas.
  • Each port runs the demo against the reference hub over HTTP.
  • CI installs the .deb, runs the container as an arbitrary user on a read-only filesystem, and lints the Helm chart.
